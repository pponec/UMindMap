# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

UMindMap is a complete, self-contained, client-only application. There is no server, no build step, no Java, and no database anywhere in the project. The entire application lives in the **`docs/`** directory, which GitHub Pages publishes as-is via the **Deploy from a branch → `/docs`** source.

**Files:**
- `docs/index.html`, `docs/app.js`, `docs/markdown.js`, `docs/svg-export.js`, `docs/style.css` — the application itself, a vanilla-JS outliner (all §4 keys, all §5 edge cases, undo/redo, JSON export/import).
- `docs/welcome.js` — the onboarding/greeting map (see below).
- `docs/images/` — locally-served images, including the app logo.
- `docs/data/` — shared, read-only demo maps and their assets (see "Shared, read-only maps" below).
- `run.html` (repo root) — a static, logic-free redirect page (meta-refresh + JS fallback) that sends the browser to `docs/index.html?welcome`; opening this one file is the standard way to launch the app.
- `run.py` and `run.java` (repo root) — optional local launchers that serve `docs/` over http (first arg = port, default 8000), useful because `localStorage` is unreliable under `file://` (opaque origin). `run.java` is a Java *source-file program* (JEP 330, JLS §7.6 relaxed) named in lower case with a class `run`, so its file name and class name do not have to be `Run`; it exists purely as a convenience http server, not as part of any server-side application logic.

**Collapse/expand:** a ▸/▾ button in the left gutter of each branch flips `node.collapsed` and re-renders. Collapse is view state, not document state, and is deliberately not pushed onto the undo stack.

**Persistence** follows the online-editor model: **`localStorage` is the continuous working store; Save/Save As are exports to disk.** Every change auto-saves (debounced 500 ms) to `localStorage['umindmap:project:' + (currentFileName || 'untitled')]`; `umindmap:last` records which project to restore on the next visit. The project name is that key's identifier. **Save As** names the project (an OS save dialog on Chromium, an in-app `<dialog>` prompt elsewhere — `window.prompt`/`confirm` are avoided, [[artifacts-block-window-modals]]) and **exports** a `.json` to disk; **Save** re-exports under the current name (or performs Save As when unnamed); **New** starts a fresh untitled project; **Open** loads a `.json`. Export uses the File System Access API when available (a real file, handle reused) and otherwise downloads; naming works everywhere even when disk export is blocked (e.g. a sandboxed iframe). The root text seeds the default name (`slugify(root.text)`).

**Project names are extension-free** — the `.json` suffix belongs only on the disk file and is not part of the identity that is the localStorage key, the URL query, and `meta.project`. `baseName()` strips it from whatever a picker or the name dialog returns (Open/Save As); the file writers append it back only when producing a real file (`suggestedName() + '.json'`, `currentFileName + '.json'`). Names that are already a key (from the URL or `umindmap:last`) are used verbatim.

**First-run onboarding:** on a first-ever visit (nothing saved yet, or `localStorage` unavailable) the app seeds a welcome/instructions map from **`docs/welcome.js`** instead of an empty project. That file holds an id-free `{text, note, children}` tree in `window.WELCOME_TREE`, which `buildDocFromTree` (in `app.js`) turns into a document with fresh node ids. Its texts and notes may carry the placeholders `{{app}}`, `{{version}}`, and `{{home}}`, filled in by `fillAppPlaceholders()` during that build (`welcome.js` loads before `app.js`, so it cannot read `APP_NAME`/`APP_VERSION`/`APP_HOME` itself). The greeting ends the root note with *"You are running UMindMap x.y.z"*, which is where the running version is surfaced in the UI, and — since it is part of the root note — in the welcome map's picture too.

The welcome map is **ephemeral**: `starterDocument()` marks it with a non-serialised `isWelcome` flag; `scheduleSave` skips persisting any doc carrying that flag (status shows `preview`), so editing it is only a preview, and it re-seeds fresh from `welcome.js` on every visit. This keeps `welcome.js` the single source of truth, with no stale greeting ever left in `localStorage`. It becomes a real, saved project only via **New**/**Open** (a fresh doc, no flag) or **Save As** (which deletes the flag before persisting).

The URL flag **`?welcome`** forces a fresh welcome map on load, even when a saved project exists, overriding the normal restore of `umindmap:last` (it sets `doc = starterDocument()`, carrying the `isWelcome` flag). Behaviour: (1) **Non-destructive** — since the welcome map is ephemeral, the visitor's stored projects stay completely intact, and a plain reload *without* the flag returns them to their own work. (2) **Self-cleaning** — on load it immediately strips `?welcome` from the address bar via `history.replaceState`, so a later reload or Save As does not re-trigger it. (3) **Always fresh** — the map re-seeds from `welcome.js` every time. (4) **Public-safe** — being non-destructive, it is safe to link publicly; the README live link points at `…/UMindMap/?welcome`. The presence check is value-agnostic (`URLSearchParams.has('welcome')`), so `?welcome`, `?welcome=1`, `?welcome=anything` all behave identically.

**The address bar also names the project:** the query is a single valueless key — the project's own localStorage name, optionally with a **`/graph`** tail asking for the picture instead of the outliner, so deleting that tail lands you in the editor of the same map. `…/` restores the last project; `…/?my-map` opens `umindmap:project:my-map`; `…/?my-map/graph` shows its graph view; `welcome` is reserved for the greeting (including the self-cleaning strip — but `?welcome/graph` keeps its address, since it is a view of a map). A name that is not in `localStorage` is not invented as an empty map: the boot falls back to the normal restore and the status line says `no project "…"`.

**Shared, read-only maps** let the site's admin publish maps everyone can open: the `.json` ending of the query key picks the source and the default view. A key **without** `.json` (`?my-map`) is a localStorage project opened in the **editor**; a key **ending** in `.json` (`?demo.json`) is a static file served from **`docs/data/`**, opened as a **graph** (a picture) and flagged `isShared`. A shared map is ephemeral like the greeting — `persistProject`/`scheduleSave` skip anything carrying `isShared` (status shows `shared`), so it is **never auto-saved** and re-fetches from the file on each visit; the admin's file stays the single source of truth. It has **no editor of its own**: the graph's *Edit map* button (`leaveGraph`) forks a personal copy — deletes `isShared`, persists under the extension-free name (`baseName`, e.g. `demo`), and navigates to `?demo` (the editor). Loading is `bootSharedFile()` (an async `fetch`), separate from the synchronous `bootLocal()` and dispatched by `urlTarget.shared`; `readUrlTarget()` returns `{ name, graph, shared }`, and `graphView = urlTarget.graph || urlTarget.shared`.

**Security for shared maps:** only a bare file name is honoured — `SHARED_NAME_RE = /^[a-z0-9._-]+\.json$/i` plus an explicit `..` reject — so there are no path segments and no traversal; a shared map can only ever be read from the one `data/` folder (fetch is same-origin `data/<file>`). A bad name, a 404, a non-map, or `file://` all fall back to the normal boot with status `no shared map "…"`. Admin workflow (see `docs/data/README.md`): Save As a map, drop the `.json` into `docs/data/`, commit — GitHub Pages serves it with no server code. `docs/data/demo.json` is a live example, alongside a set of `demo-*.json` stress maps. `updateFileLabel()` keeps the address in sync with whichever project is actually open.

Every document carries a stable hidden `id` in its JSON (`ensureDocId`), a stable identifier scoped to the document itself.

**Drag-and-drop** reordering/re-parenting is implemented behind a `DND_ENABLED` flag in `app.js`: drag a node by its gutter grip and drop it before/after another node at any level; dropping into the node's own subtree or as a sibling of the root is blocked. It is self-contained (the flag, a grip block in `buildNodeLi`, a "Drag and drop" JS section, and `.drag-grip`/`.drop-*` CSS), so it can be disabled with one flag.

**SVG export** lives entirely in **`docs/svg-export.js`**, which exposes exactly one global, `documentToSvg(doc, opts)` → SVG source (`opts.project` names the project in the footer). Showing or saving that string is `app.js`'s responsibility: one `downloadBlob(text, type, name)` serves the JSON export, the picture download, and the popup-blocked fallback. The toolbar's *Show graph* button calls `exportSvgFile()` in `app.js`, which opens **`…/?project/graph`** in a new tab — a real, reloadable, bookmarkable, shareable address rather than a throw-away blob — after flushing the debounced save so the new tab reads the current text. That address is the same `index.html` in **graph view** (`showGraph()`): the workspace and footer are hidden, the editing buttons give way to *Edit map* and *Download SVG*, and the picture is inlined into `#graph-canvas`, which scrolls horizontally. Which control belongs to which mode is stated once, in markup and CSS (`.edit-only` / `.graph-only` under `body.graph-view`).

Toolbar buttons carry discreet monochrome icons above a 760 px mobile breakpoint (below it the labels stand alone): each icon is a tiny inline SVG in a `--icon` custom property, painted as a CSS mask over `background-color: currentColor`, so one glyph set follows the button's own colour into the dark theme. `-webkit-mask` is required down to the Chrome 105 / Safari 15.4 floor. The header keeps the logo and wordmark exactly as the editor has them; only the project name and the save status go away with the editing buttons, and there is no frame around the sheet. Hiding uses the `hidden` attribute, so `.workspace[hidden]`/`.help[hidden]` need an explicit `display: none` (an author `display` beats the UA rule).

Only a map whose address cannot be rebuilt falls back to a blob URL and `window.open` (which must stay synchronous inside the click handler, or the popup blocker kills it; when it is blocked anyway — e.g. a sandboxed iframe — it downloads instead): that covers a stored project with no accessible `localStorage` (`file://`). The greeting is always addressable, storage or not, because `?welcome/graph` re-seeds it from `welcome.js`; `addressableMap()` holds this rule. The welcome map reaches `persistProject()` (to flush any pending save before a new tab reads storage); the invariant "the greeting is never persisted" lives inside `persistProject()` itself, so every caller gets it automatically. Save As still works because it deletes `isWelcome` first, which is precisely what turns the preview into a project.

**The exported sheet signs itself** in the bottom-right corner, over a hairline: logo, `UMindMap` in the brand blue, the project's localStorage name, and the export date as `yyyy-MM-dd` (local time, not UTC). It sits at the end of the sheet, below the map. The logo is rasterised at load time from `docs/images/umindmap-logo.png` onto a 36 px canvas and embedded as a data URI (~5 kB); code that draws at page load (the graph view does) awaits `whenLogoReady()` first, so the drawing never races the source image. When the logo cannot be embedded (a tainted canvas under `file://`, or a missing file), the footer stays text-only and the reason is logged. The canvas widens when the footer is broader than the map, in which case a small map is centred over it.

**The drawing is a two-sided mind map:** root centred; up to 3 branches all go right, otherwise the first ⌊N/2⌋ go right and the rest left, both in source order top to bottom (the left side is mirrored, not rotated). Labels are one line, measured with a canvas 2D context and truncated with `…` past `MAX_BOX_W`; columns widen so the widest box still leaves a readable connector. A wide per-depth floor `COL_MIN` (300/330 px) exists only so a parent's hanging note bubble (width `NOTE_W`) clears the child column, so `columns()` applies it only on depths where a parent actually hangs a note — `layout()` computes `hangDepths` (depths with a note-bearing parent; the root is excluded, since its note sits centred below it, not in a column gap); elsewhere a column shrinks to just `prev + LINK_MIN`. Connectors are cubic Béziers; the palette is always light (print/share), regardless of the app theme; `collapsed` is ignored, so everything is drawn expanded.

A node's `note` becomes a UML-style bubble: a leaf's note sits in the outer gutter level with its node; a parent's note hangs directly below its own node, flush with the node's inner edge, so it stays out of both the incoming connector's corridor and the child column (`COL_MIN` > `NOTE_W`); the root's note goes in the free strip below the root. Layout runs in two passes, since the vertical pass tests real rectangles and therefore needs x first: (1) labels, widths, column offsets, x; (2) y. In pass 2 a node plus its bubble, its connector corridors, and its whole subtree form a rigid group: leaves are handed out on a plain `SLOT` grid, a parent sits at the mean of its children, and each group slides down only as far as an actual rectangle collision demands (`slideDown` against the side's occupancy list, the group's own rectangles excluded). A tall note costs height only in the column it actually occupies, so a branch can rise into the space beside a neighbour's long note instead of below it.

Connector corridors are reserved as `FAN_SLICES` pieces per link rather than one bounding box, since the cubic is monotone in both axes and each slice is exactly the curve's extent there. Corridors test on strict overlap (`collides` drops the `NOTE_GAP` clearance when either rectangle is a corridor), so a bubble flush with a column is not treated as sitting inside one. A bubble much wider than its node would sit in its own outgoing fan; `hangCrosses()` samples the link cubics against it (using the narrowest column gap the drawing can end up with) and, if it crosses, that node falls back to a lane below its whole subtree, where no connector reaches.

**Bubble bodies are real Markdown** — the app's `renderMarkdown` output inside an SVG `<foreignObject>`, serialised with `XMLSerializer` (not `innerHTML`, whose `<br>`/`<img>` would break XML parsing) and measured in a hidden host so the reserved height is exact. Nothing in a note is clipped: there is no maximum bubble height; code blocks get `white-space: pre-wrap`; long words/URLs/table cells get `overflow-wrap`; the measured height carries `NOTE_SLACK` spare pixels in case the viewer's fonts wrap a line differently.

A note may contain a Markdown image (`![alt](data/…​.png)`; the renderer allows a `data:` scheme for images but not for links). Because `measureNotes` reads `offsetHeight` synchronously, `whenNotesReady(doc)` preloads every note image (the same pattern as `whenLogoReady()`, awaited beside it in `showGraph`/`downloadSvgFile`) into a `noteImgSize` cache, and `buildNote` stamps each `<img>` with `width`/`height` from that cache so the browser reserves the aspect-ratio box before the pixels arrive (`.umnote img` is `max-width:100%; height:auto`). Note images are resolved to an absolute URL (`absolute()`), so a downloaded SVG shows them only while online, unlike the footer logo, which is embedded as a data URI. `docs/data/train-ticket.png` is a shared image asset used by `demo-trip.json` and `demo-markdown-notes.json`.

The `<style>` block inside the SVG is wrapped in `/* <![CDATA[ */ … /* ]]> */`, since the file is parsed as XML and a raw `<` in the CSS would start a tag; the markers sit inside CSS comments, so the CSS stays valid when the SVG is inlined into an HTML page instead. `<foreignObject>` renders in browsers but not in Inkscape/librsvg or when rasterising to PNG — an accepted trade-off. Layout runs on a private copy of the tree (`layoutTree`), so scratch coordinates never reach undo snapshots or `localStorage`.

**Stress/demo maps** for the picture live in `docs/data/` as `demo-*.json` (note sizes, five levels of nesting, mixed branch shapes, a note on every node, Markdown and escaping); `docs/data/README.md` documents what each one stresses. Being in the shared folder, each is a live, read-only graph — open e.g. `?demo-note-sizes.json`, or fork it with *Edit map* to work on it in the editor.

## What UMindMap is

A minimalist, self-hosted, purely client-side mind-mapping app. Core insight: the browser already provides tree (DOM), layout (CSS), and editing (`contenteditable`), so the app writes no rendering engine and no layout algorithm. The app is an **outliner**: a nested list of editable nodes. All state lives in the browser (`localStorage`) and in `.json` files the user exports and re-opens; nothing is ever sent to a server.

## Locked decisions (do not re-litigate during build)

- **UI model:** outliner (nested `<ul>/<li>`), NOT free-positioned nodes on a canvas.
- **Node positioning:** computed by CSS/browser in the editor. No custom layout algorithm there.
- **Text editing:** `contenteditable` per node; serialised to plain text.
- **Connector lines:** none in the outliner — hierarchy is shown by CSS indentation and vertical guide lines. SVG connectors exist only in the generated graph/picture view.
- **Frontend:** vanilla JS, no framework, no build step. `docs/index.html` plus `.js`/`.css` files.
- **Persistence:** the whole document at once, debounced (500 ms) into `localStorage`; explicit export/import of the whole document as one `.json` file on disk. No diffs, no database, no server.
- **Undo/redo:** a snapshot of the full JSON state pushed onto a stack. NOT a command pattern.
- **Auth:** none — the app has no accounts and no server to authenticate against.

## Data model

A recursive tree via `children` (no flat node map). Node: `{ "id", "text", "note", "collapsed", "children": [] }`. `note` is an optional longer free-text description per node, edited in a modal dialog (Alt+Enter on the focused node, or the detail panel's Edit button), trimmed on serialisation, empty when unset. Nodes with a note show a 🗒 marker after their text — a separate, non-editable `.note-mark` span sharing a flex `.row` with the contenteditable `.node` (kept out of the editable region so typing never displaces it; clicking it opens the description).

The focused node's `note` is shown in a right-hand detail panel, rendered as **Markdown** by an in-house renderer in **`markdown.js`** (loaded before `app.js`; exposes the global `renderMarkdown(md)` → HTML string, plus `renderMarkdownInto(parent, md)`). Supported syntax: headings 1–6, unordered/ordered lists, blockquotes, fenced and indented code blocks, horizontal rules, GFM tables, paragraphs with hard breaks (trailing `\`), and inline `code`/**bold**/_italic_/links/images. Output is built as DOM nodes, so all text is escaped via `textContent` (no separate sanitisation step), and `javascript:`/`vbscript:`/`data:` link schemes are blocked. This JS renderer is the single Markdown implementation used anywhere in the app.

Document: `{ "meta": {…}, "version": 1, "rootId", "root": {…} }`. Every serialised document opens with a **file header** — since JSON has no comments, this is expressed as data: `meta` = `{ app, version, home, project, exported }`, i.e. `"UMindMap"`, `APP_VERSION` (the app's own version, `1.0.0`, declared beside `APP_NAME`/`APP_HOME` at the top of `app.js`), the project home page, the **project name** (`currentFileName`, the map's localStorage key, extension-free — omitted while the map is still unnamed), and the export time as `yyyy-MM-DD HH:mm` in local time (`exportStamp()`; the SVG footer keeps its own date-only `isoDate()`). `meta` is built fresh by `fileMeta()` inside `serialise()`, covering both the disk export and the `localStorage` copy. `ensureDocId()` deletes this header on load, so the in-memory `doc` stays a pure model. The sample maps in `docs/data/` carry the same header. `id` is a short random string generated on the client (`"n_" + base36`). `collapsed` controls only the display of children; data is retained regardless.

## Keyboard model (core UX — low-mouse)

`Enter` = new sibling below current + focus it; `Tab` = indent (become child of previous sibling); `Shift+Tab` = outdent (become sibling of parent); `↑`/`↓` = focus prev/next visible node; `Alt+↑`/`Alt+↓` = reorder the node among its siblings (no-op at the ends); `Backspace` on an empty node = delete it, focus the previous node, reparent its children to the parent; `Ctrl+Z` / `Ctrl+Shift+Z` = undo/redo. The mouse is also supported: dragging the ⠿ grip moves a branch, and clicking ▸/▾ folds one away.

## Predecided edge cases (honor these)

- `Shift+Tab` on a node directly under root: no-op (don't crash).
- `Tab` on the first sibling (no previous sibling): no-op.
- Deleting the root: forbidden; root is always present.
- Empty node serialises as `text: ""` (allowed).
- Reading `contenteditable` text: use `element.innerText`, not `innerHTML`; trim, replace non-breaking space with a normal space, ignore injected `<br>`/`<div>`.
- Paste: intercept `paste`, insert plain text only (`clipboardData.getData('text/plain')`), prevent default HTML paste.
- IME/diacritics: don't act on `keydown` while `event.isComposing` is true.

## Explicitly out of scope

Real-time collaboration, multiple users, cloud sync, mobile-specific gestures, any server or backend, pixel positioning in the editor, a custom layout algorithm in the editor, a database, and user authentication.

## Code conventions

- **Build:** none. The app is a static file set in `docs/`; no build tool of any kind is involved. To run it: open `run.html` (redirects to `docs/index.html?welcome`), or serve `docs/` locally via `run.py`/`run.java` when `localStorage` under `file://` needs to be reliable.
- **JS:** vanilla, no dependencies, English names and comments.
- **Single source of truth for the tree; rendering is a pure function of state (`renderTree(doc)`)**.
- **Markdown:** a single, self-contained implementation in `docs/markdown.js`.

## Working with the spec author

The author cannot see the running app — most real-time interaction happens through a test loop. When reporting a bug, state: (1) what you did, (2) what happened, (3) what you expected — and include the exported JSON when structure is involved.
