## Project state

`assignment.md` (written in Czech) is the authoritative spec: it pre-decides everything that would otherwise need a clarification round, so read it before starting work. The notes below summarize its binding decisions in English.

**Phase 0 (clickable prototype, no Java) is implemented** in the **`docs/`** directory as five files — `index.html`, `app.js`, `markdown.js`, `svg-export.js`, `style.css` (plus `docs/.nojekyll` and a `docs/images/` folder for locally-served images) — a working vanilla-JS outliner (all §4 keys, §5 edge cases, undo/redo, JSON export/import). It runs standalone via `file://`, and GitHub Pages publishes it as-is via the **Deploy from a branch → `/docs`** source; `docs/` keeps the repo root free for a future Java/Maven build. (The files previously lived in a `prototype/` helper directory; it was removed and they were moved into `docs/` for static hosting, dropping the earlier plan to relocate them under `src/main/webapp/`.) The local launchers `run.py` and `run.java` serve `docs/` over http (optional first arg = port, default 8000). The Java one is deliberately lower-case, class `run` included: it is a script, not a compiled class (source-file mode per JEP 330 relaxes JLS §7.6, so neither the file name nor the class name has to be `Run`), and the name pairs it with `run.py` in the repo root. Per-branch **collapse/expand toggles** (a Phase-2 item) are already built in: a ▸/▾ button in the left gutter flips `node.collapsed` and re-renders; collapse is treated as view state and is deliberately not pushed onto the undo stack. **Persistence** (Phase-0 stand-in for the server) follows the online-editor model: **localStorage is the continuous working store; Save/Save As are exports.** Every change auto-saves (debounced 500 ms — the cadence Phase 1's server save reuses) to `localStorage['umind:project:' + (currentFileName || 'untitled')]`; `umind:last` records which project to restore next visit. The project name is that key's identifier. **Save As** names the project (OS save dialog on Chromium, an in-app `<dialog>` prompt elsewhere — `window.prompt`/`confirm` are avoided, [[artifacts-block-window-modals]]) and **exports** a `.json` to disk; **Save** re-exports under the current name (or does Save As when unnamed); **New** starts a fresh untitled project; **Open** loads a `.json`. Export uses the File System Access API when available (a real file, handle reused) and otherwise downloads; naming works everywhere even when disk export is blocked (sandbox). The root text seeds the default name (`slugify(root.text)`). **The project name is extension-free** — the `.json` suffix belongs only on the disk file and is *not* part of the identity that is the localStorage key, the URL query and `meta.project`; `baseName()` strips it from whatever a picker or the name dialog returns (Open/Save As), and the file writers append it back only when producing a real file (`suggestedName() + '.json'`, `currentFileName + '.json'`). Names that are *already* a key (from the URL or `umind:last`) are used verbatim, so a project saved under an older `…​.json` key still loads until it is next re-saved under its clean name. localStorage is unreliable under `file://` (opaque origin), so serve over http/localhost. **First-run onboarding:** on a first-ever visit (nothing saved yet, or when localStorage is unavailable) the app seeds a welcome/instructions map from **`docs/welcome.js`** instead of an empty project — that file holds an id-free `{text, note, children}` tree in `window.WELCOME_TREE`, which `buildDocFromTree` (in `app.js`) turns into a document with fresh node ids. Its texts and notes may carry the placeholders `{{app}}`, `{{version}}` and `{{home}}`, filled in by `fillAppPlaceholders()` during that build — `welcome.js` is loaded *before* `app.js` and so cannot read `APP_NAME`/`APP_VERSION`/`APP_HOME` itself; the greeting uses it to end the root note with *"You are running UMind x.y.z"*, which is where the running version is visible in the UI (and, since it is part of the root note, in the welcome map's picture too). The welcome map is **ephemeral**: `starterDocument()` marks it with a non-serialised `isWelcome` flag, `scheduleSave` skips persisting any doc carrying that flag (status shows `preview`), so editing it is only a preview and it **re-seeds fresh from `welcome.js` on every visit** — keeping `welcome.js` the single source of truth with no stale greeting left in localStorage (so edits to `welcome.js` always show on the next reload). It becomes a real, saved project only via **New**/**Open** (fresh doc, no flag) or **Save As** (which `delete`s the flag before persisting). The URL flag **`?welcome`** forces a fresh welcome map on load **even when a saved project exists**, overriding the normal restore of `umind:last` (it simply sets `doc = starterDocument()`, carrying the `isWelcome` flag). Its full behaviour: (1) **Non-destructive** — because the welcome map is ephemeral (`isWelcome`, never persisted; see above), the visitor's stored projects stay completely intact and a plain reload *without* the flag returns them to their own work. (2) **Self-cleaning** — on load it immediately strips `?welcome` from the address bar via `history.replaceState`, so a later reload or Save As does not re-trigger it. (3) **Always fresh** — the map is re-seeded from `welcome.js` every time, so the flag is the reliable way to preview `welcome.js` edits regardless of what is saved locally. (4) **Public-safe** — being non-destructive, it is safe to link publicly; the README live link points at `…/UMind/?welcome`. The presence check is value-agnostic (`URLSearchParams.has('welcome')`), so `?welcome`, `?welcome=1`, `?welcome=anything` all behave identically. **The address bar also names the project** (added later): the query is a single valueless key — the project's own localStorage name, optionally with a **`/graph`** tail asking for the picture instead of the outliner, so deleting that tail lands you in the editor of the same map. `…/` restores the last project as before, `…/?my-map` opens `umind:project:my-map`, `…/?my-map/graph` shows its graph view, and `welcome` stays reserved for the greeting (unchanged, including the self-cleaning strip — but `?welcome/graph` keeps its address, since it is a view of a map). A name that is not in localStorage is not invented as an empty map: the boot falls back to the normal restore and the status line says `no project "…"`. **Shared, read-only maps** (added later) let the site's admin publish maps everyone can open: the `.json` ending of the query key picks the source and the default view — a key **without** `.json` (`?my-map`) is a localStorage project opened in the **editor** (as above), a key **ending** `.json` (`?demo.json`) is a static file served from the **`docs/data/`** folder, opened as a **graph** (a picture) and flagged `isShared`. A shared map is ephemeral like the greeting — `persistProject`/`scheduleSave` skip anything carrying `isShared` (status shows `shared`), so it is **never auto-saved** and re-fetches from the file each visit (the admin's file stays the single source of truth). It has **no editor of its own**: the graph's *Edit map* button (`leaveGraph`) forks a personal copy — it deletes `isShared`, persists under the extension-free name (`baseName`, e.g. `demo`) and navigates to `?demo` (the editor) — so the first save happens only when the reader chooses to edit, and the shared file itself is never modified. Loading is `bootSharedFile()` (async `fetch`), split out from the synchronous `bootLocal()` and dispatched by `urlTarget.shared`; `readUrlTarget()` now returns `{ name, graph, shared }` and `graphView = urlTarget.graph || urlTarget.shared`. **Security:** only a bare file name is honoured — `SHARED_NAME_RE = /^[a-z0-9._-]+\.json$/i` plus an explicit `..` reject — so there are **no path segments and no traversal**; a shared map can only ever be read from that one `data/` folder (fetch is same-origin `data/<file>`). A bad name, a 404, a non-map or `file://` all fall back to the normal boot with status `no shared map "…"`. Admin workflow (see `docs/data/README.md`): Save As a map, drop the `.json` into `docs/data/`, commit — GitHub Pages serves it with no server code; `docs/data/demo.json` is a live example (with a set of `demo-*.json` stress maps beside it). `updateFileLabel()` syncs the address to the project actually open, so a Save As does not leave a link pointing at the old name. Read it with `readUrlTarget()` -> `{ name, graph, shared }`. There is deliberately **no** destructive counterpart: an earlier `?welcome=reset` that wiped every `umind:` key (via a `clearStoredProjects` helper) was removed as a silent, undiscoverable footgun whose original rationale — clearing a stale *stored* welcome copy — no longer applies now that the welcome map is ephemeral; any future "start over" should be an in-app button with confirmation, not a hidden URL. Each document carries a stable hidden `id` in its JSON (`ensureDocId`), ready to become `/api/map/{id}` in Phase 1. **Drag-and-drop** reordering/re-parenting (a Phase-2 item, explicitly out of the original MVP per §8) is implemented behind a `DND_ENABLED` flag in `app.js`: drag a node by its gutter grip and drop before/after another node at any level; dropping into the node's own subtree or as a sibling of the root is blocked. It is intentionally self-contained (flag + grip block in `buildNodeLi` + a "Drag and drop" JS section + `.drag-grip`/`.drop-*` CSS) so it can be disabled with one flag or removed cleanly. **SVG export** (a Phase-2 item) lives entirely in **`docs/svg-export.js`**, which exposes exactly one global, `documentToSvg(doc, opts)` → SVG source (`opts.project` names the project in the footer); *showing or saving* that string is `app.js`'s business, so every blob/tab/download path sits there beside the existing file handling — one `downloadBlob(text, type, name)` serves the JSON export, the picture download and the popup-blocked fallback. The toolbar's *Show graph* button calls `exportSvgFile()` in `app.js`, which opens **`…/?project/graph`** in a new tab — a real address that can be reloaded, bookmarked and shared, rather than a throw-away blob — after flushing the debounced save so the new tab reads the current text. That address is the same `index.html` in **graph view** (`showGraph()`): the workspace and the footer are hidden, the editing buttons give way to *Edit map* and *Download SVG*, and the picture is inlined into `#graph-canvas`, which scrolls horizontally. Which control belongs to which mode is stated once, in the markup and CSS (`.edit-only` / `.graph-only` under `body.graph-view`) rather than in a hard-coded id list in the script. The toolbar buttons carry discreet monochrome icons above the 760 px mobile breakpoint (below it the bar is already tight, so the labels stand alone): each is a tiny inline SVG in a `--icon` custom property, painted as a **CSS mask** over `background-color: currentColor`, so one set of glyphs follows the button's own colour into the dark theme instead of needing a second set. `-webkit-mask` is still required at the Chrome 105 / Safari 15.4 floor. The header keeps the logo and the wordmark exactly as the editor has them; only the project name and the status (which is about saving) go away with the editing buttons, and there is no frame around the sheet. Hiding uses the `hidden` attribute, so `.workspace[hidden]`/`.help[hidden]` need an explicit `display: none` — an author `display` beats the UA rule (same trap as `.detail-editor[hidden]`). A **separate viewer page was considered and rejected**: with two files the address would have to be `graph.html?x`, and deleting the tail would no longer reach the editor — the truncation rule only works while both views share one URL path. Only a map the address cannot rebuild falls back to the blob URL and `window.open` (which must stay synchronous inside the click handler or the popup blocker kills it; when it is blocked anyway — sandboxed iframe — it downloads instead): that is a stored project with no localStorage to read it back from (`file://`). The greeting is *always* addressable, storage or not, because `?welcome/graph` re-seeds it from `welcome.js` — the blob was used there at first to preserve unsaved preview edits, but that made the one map everybody meets open under a `blob:` address, and a preview that is explicitly never saved has no edits worth preserving. `addressableMap()` holds that rule. Since the welcome map now reaches `persistProject()` (to flush the pending save before the new tab reads storage), the "never persist the greeting" invariant moved *into* `persistProject()` instead of living in each caller — Save As still works because it deletes `isWelcome` first, which is precisely what turns the preview into a project. The sheet signs itself in the **bottom-right corner**, over a hairline: logo, `UMind` in the brand blue, the project's localStorage name and the export date as `yyyy-MM-dd` (local time, not UTC) — so a saved or forwarded picture says what it is and when it was made. It sits at the *end* of the sheet because a header duplicated the app name of the page hosting it, one line below the other. The logo is rasterised at load time from `docs/images/umind-logo.png` onto a 36 px canvas and embedded as a data URI (~5 kB), so that file stays the single source of truth and the 1 MB original is never shipped. That load is asynchronous while `documentToSvg` is not, so anything drawing at page load — the graph view does — must `await whenLogoReady()` first or it races the 1 MB source image and signs the sheet without a logo (on localhost the image lands in ~50 ms and the race is usually won, which is what makes the bug intermittent). When the logo genuinely cannot be embedded — canvas tainted under `file://`, or the file missing — the footer stays text-only and the reason is logged, rather than looking like a silent bug. The canvas widens when the footer is broader than the map (a small map is then centred over it). The drawing is a two-sided mind map: root centred, up to 3 branches all go right, otherwise the first ⌊N/2⌋ go right and the rest left, both in source order top to bottom (the left side is **mirrored, not rotated**). Labels are one line (measured with a canvas 2D context, truncated with `…` past `MAX_BOX_W`), columns widen so the widest box still leaves a readable connector. The wide per-depth floor `COL_MIN` (300/330 px) exists **only** so a parent's hanging note bubble (width `NOTE_W`) clears the child column, so `columns()` applies it **only on depths where a parent actually hangs a note** — `layout()` computes `hangDepths` (depths with a note-bearing parent, the root excluded because its note sits centred below it, not in a column gap) and elsewhere a column shrinks to just `prev + LINK_MIN`; otherwise a map whose parents carry no note (notes only on leaves, which go to the gutter) sat in over-wide columns with long empty connectors. Connectors are cubic Béziers, the palette is **always light** (print/share) regardless of the app theme, and `collapsed` is ignored — everything is drawn expanded. A node's `note` becomes a UML-style bubble: a leaf's sits in the outer gutter level with its node, a parent's **hangs directly below its own node** flush with the node's inner edge (so it stays out of both the incoming connector's corridor and the child column, since `COL_MIN` > `NOTE_W`), and the root's goes in the free strip below the root. Layout runs in two passes, because the vertical one tests real rectangles and therefore needs x: **(1)** labels, widths, column offsets and x; **(2)** y. In pass 2 a node *plus its bubble, its connector corridors and its whole subtree* is a **rigid group**: leaves are handed out on a plain `SLOT` grid, a parent sits at the mean of its children, and each group then slides down only as far as an actual rectangle collision demands (`slideDown` against the side's occupancy list, the group's own rectangles excluded). That is the key to compactness — a tall note costs height only in the column it actually occupies, so a branch can rise into the space *beside* a neighbour's long note instead of below it (on the welcome map a 15-line leaf note costs 6 px instead of 201 px). Connector corridors are reserved as `FAN_SLICES` pieces per link rather than one bounding box: the cubic is monotone in both axes, so each slice is exactly the curve's extent there and the staircase hugs the curve — a whole-corridor box would cost ~70 px of needless height. Corridors test on strict overlap (`collides` drops the `NOTE_GAP` clearance when either rectangle is a corridor), otherwise every bubble flush with a column would count as sitting inside one. A bubble much wider than its node would sit in its *own* outgoing fan, which no collision test can catch (own rectangles are excluded), so `hangCrosses()` samples the link cubics against it — using the narrowest column gap the drawing can still end up with, the worst case — and that node falls back to a lane below its whole subtree, where no connector reaches. Bubble bodies are **real Markdown** — the app's `renderMarkdown` output inside an SVG `<foreignObject>`, serialised with `XMLSerializer` (not `innerHTML`, whose `<br>`/`<img>` would break XML parsing) and measured in a hidden host so the reserved height is exact. **Nothing in a note may be clipped**, because a `<foreignObject>` silently cuts off whatever does not fit its rectangle: there is deliberately no maximum bubble height (an earlier `NOTE_MAX_H` of 300 px truncated long notes), code blocks get `white-space: pre-wrap` (a `pre` does not wrap by default, so a long line ran out of the bubble), long words/URLs/table cells get `overflow-wrap`, and the measured height carries `NOTE_SLACK` spare pixels in case the viewer's fonts wrap a line differently than ours did. **A note may contain a Markdown image** (`![alt](data/…​.png)`; the app's renderer allows a `data:` scheme for images but not for links): because `measureNotes` reads `offsetHeight` *synchronously*, an image that has not decoded yet would be measured at height 0 and then clipped — so `whenNotesReady(doc)` preloads every note image (same pattern as `whenLogoReady()`, awaited beside it in `showGraph`/`downloadSvgFile`) into a `noteImgSize` cache, and `buildNote` stamps each `<img>` with `width`/`height` attributes from that cache so the browser reserves the aspect-ratio box before the pixels arrive (`.umnote img` is `max-width:100%; height:auto`). Note images are resolved to an absolute URL (`absolute()`), so a downloaded SVG shows them only while online — unlike the footer logo, which is embedded as a data URI. `docs/data/train-ticket.png` is the one shared image asset, used by `demo-trip.json` (the README showcase, in the *Book the train early* note) and `demo-markdown-notes.json`. The `<style>` block is wrapped in `/* <![CDATA[ */ … /* ]]> */`: the file is parsed as XML, where a raw `<` in the CSS starts a tag (a comment mentioning a `pre` tag broke every export once), while the markers sitting inside CSS comments keep the CSS valid when the SVG is inlined into an HTML page instead. Trade-off, accepted: `<foreignObject>` renders in browsers but **not** in Inkscape/librsvg or when rasterising to PNG. Layout runs on a private copy of the tree (`layoutTree`), so scratch coordinates never reach undo snapshots or localStorage. **Stress / demo maps** for the picture live in **`docs/data/`** as `demo-*.json` (note sizes, five levels of nesting, mixed branch shapes, a note on every node, Markdown and escaping; `docs/data/README.md` says what each one stresses). Being in the shared folder, each is a live read-only graph — open e.g. `?demo-note-sizes.json`, or fork it with *Edit map* to poke at it in the editor (they used to live in a repo-root `test/json/` loaded only via *Open…*; moved so they double as shareable demos). **The Maven build and the servlets do not exist yet** — Phase 1 and 2 are not started.

## What UMind is

A minimalist, self-hosted mind-mapping app. Core insight: the browser already provides tree (DOM), layout (CSS), and editing (`contenteditable`) — so **we write no rendering engine and no layout algorithm.** The app is an **outliner**: a nested list of editable nodes. Java does persistence only (accept JSON → store; load JSON → return); no map logic lives on the server.

## Locked decisions (do not re-litigate during build)

- **UI model:** outliner (nested `<ul>/<li>`), NOT free-positioned nodes on a canvas.
- **Node positioning:** computed by CSS/browser. No custom layout algorithm.
- **Text editing:** `contenteditable` per node; serialize to plain text.
- **Connector lines:** none in MVP — hierarchy is shown by CSS indentation + vertical guide lines. SVG connectors are phase 2.
- **Frontend:** vanilla JS, no framework, no build step. One `.html` + `.js` + `.css`.
- **Java:** Jakarta Servlet (`jakarta.servlet`), plain `HttpServlet`.
- **Persistence:** whole document at once, debounced (500 ms) POST to one endpoint. No diffs. Storage = one JSON file per map, `{id}.json`, on disk. No database.
- **Undo/redo:** snapshot the full JSON state onto a stack. NOT a command pattern.
- **Auth:** none in MVP.

## Data model

Recursive tree via `children` (no flat node map in MVP). Node: `{ "id", "text", "note", "collapsed", "children": [] }`. `note` is an optional longer free-text description per node (added beyond the original spec), edited in a modal dialog (Alt+Enter on the focused node, or the detail panel's Edit button), trimmed on serialization, empty when unset. Nodes with a note show a 🗒 marker after their text — a separate non-editable `.note-mark` span sharing a flex `.row` with the contenteditable `.node` (kept out of the editable so typing never displaces it; clicking it opens the description). The focused node's `note` is shown in a right-hand detail panel rendered as **Markdown** by an in-house renderer in its own file **`markdown.js`** (loaded before `app.js`; exposes the global `renderMarkdown(md)` → HTML string, plus `renderMarkdownInto(parent, md)`). It is a JS port of Ujorm's `MarkdownToHtmlConverter` (`ujo-web`): headings 1–6, unordered/ordered lists, blockquotes, fenced and indented code blocks, horizontal rules, GFM tables, paragraphs with hard breaks (trailing `\`), and inline `code`/**bold**/_italic_/links/images. It builds the output as DOM nodes, so all text is escaped via `textContent` (no separate sanitization) and `javascript:`/`vbscript:`/`data:` link schemes are blocked. The Java `MarkdownToHtmlConverter` is intentionally *not* used on the server (the earlier "Java renderer" plan is dropped) — this JS renderer is the single Markdown implementation. Document: `{ "meta": {…}, "version": 1, "rootId", "root": {…} }`. Every serialised document opens with a **file header** — JSON has no comments, so it is data: `meta` = `{ app, version, home, project, exported }`, i.e. `"UMind"`, `APP_VERSION` (the app's own version, `1.0.0`, declared beside `APP_NAME`/`APP_HOME` at the top of `app.js` — bump it on release), the project home page, the **project name** (`currentFileName`, i.e. the map's localStorage key, extension-free — the `.json` suffix lives only on the disk file, never in the key/URL/`meta.project`; omitted while the map is still unnamed: a fresh untitled doc or the ephemeral welcome map), and the export time as `yyyy-MM-DD HH:mm` in local time (`exportStamp()`; the SVG footer keeps its own date-only `isoDate()`). It is named **`meta`** (not the earlier `generator`) because it now also carries the project name, which describes the *document*, not the tool that produced it. It is built fresh by `fileMeta()` inside `serialise()`, so it covers the disk export *and* the localStorage copy, and no file ever carries the stamp of the app version that wrote its previous revision; `ensureDocId()` deletes it on load (both `meta` and the legacy `generator`, so pre-rename files still load cleanly) so the in-memory `doc` stays the pure model. The sample maps in `docs/data/` carry the same header. `id` is a short random string generated on the client (`"n_" + base36`). `collapsed` only controls display of children; data is retained.

## Servlet API (phase 1)

| Method | Path | Body | Response |
|---|---|---|---|
| `GET`  | `/api/map/{id}` | — | Document JSON (or empty root if it doesn't exist) |
| `POST` | `/api/map/{id}` | Document JSON | `200 OK` |
| `GET`  | `/api/map/{id}/export?format=json` | — | File download (phase 2: `svg`, `png`) |

Server is stateless — no session. `{id}.json` lives in a configured directory.

## Build order (optimized for fastest running state)

- **Phase 0 — clickable prototype, no Java.** Standalone HTML/JS/CSS: outliner, all keyboard shortcuts, undo/redo, in-memory JSON serialization (an "Export JSON" button into a textarea). **This is the largest part of the work** — the interaction and edge cases are ironed out here before any backend exists.
- **Phase 1 — persistence.** Add the three servlets; frontend does `load` on start and debounced `save` on change, replacing the in-memory export with API calls.
- **Phase 2 — optional add-ons (separate iterations):** SVG connector overlay computed from `getBoundingClientRect()`, collapse/expand buttons, SVG/PNG export, `.mm` (FreeMind/Freeplane) import/export, node icons/colors.

## Keyboard model (core UX — low-mouse)

`Enter` = new sibling below current + focus it; `Tab` = indent (become child of previous sibling); `Shift+Tab` = outdent (become sibling of parent); `↑`/`↓` = focus prev/next visible node; `Alt+↑`/`Alt+↓` = reorder the node among its siblings (no-op at the ends; added beyond the original spec); `Backspace` on empty node = delete, focus previous, reparent its children to the parent; `Ctrl+Z` / `Ctrl+Shift+Z` = undo/redo.

## Predecided edge cases (honor these — they exist to save iterations)

- `Shift+Tab` on a node directly under root: no-op (don't crash).
- `Tab` on the first sibling (no previous sibling): no-op.
- Deleting the root: forbidden; root is always present.
- Empty node serializes as `text: ""` (allowed).
- Reading `contenteditable` text: use `element.innerText`, not `innerHTML`; trim, replace ` ` with space, ignore injected `<br>`/`<div>`.
- Paste: intercept `paste`, insert plain text only (`clipboardData.getData('text/plain')`), prevent default HTML paste.
- IME/diacritics: don't act on `keydown` while `event.isComposing` is true.

## Explicitly out of scope (MVP)

Real-time collaboration, multi-user, cloud sync, mobile gestures, mouse drag-and-drop reorg (keyboard only for now), pixel positioning, custom layout algorithm, DB, auth.

## Code conventions (from the spec)

- **Build:** Maven project, Java 17, with a Maven Wrapper (`mvnw`) committed at the project root. Once scaffolded, typical commands: `./mvnw package`, `./mvnw test`, single test via `./mvnw test -Dtest=ClassName#method`.
- **Servlet implementation:** use the `Element` class from the `ujo-web` module of the Ujorm library — see https://github.com/pponec/ujorm/blob/ujorm3/README_ELEMENT.md
- **Java:** use `var` for locals; English names and comments; JavaDoc comment above each method. Prefer `switch` over `if` where applicable.
- **Logging:** use the standard logging library; default level WARNING.
- **JS:** vanilla, no dependencies, English comments.
- **Single source of truth for the tree; render is a pure function of state (`renderTree(doc)`).**

## Working with the spec author

The author cannot see the running app — most real time is the test loop. When reporting a bug, state: (1) what you did, (2) what happened, (3) what you expected — and include the exported JSON when structure is involved.
